When a credential outlives its authority

A tiny interactive state machine: what should happen to access when the account behind a credential is no longer active?

Fictional systemRuns locally in your browserNo network requests

The invariant

Authentication is not just a property of a token. Authorization often depends on the current state of the account, the token's validity, and the action being requested. In this illustrative model, the secure rule is simple: access requires both an issued token and an active account.

Interactive state test

Change the system state

First issue a token; then delete the fictional account. Compare the two authorization implementations below.

ACCOUNT: ACTIVE   /   TOKEN: NONE

Fragile implementation

Token-only check

Checks only whether a token was previously issued. Ignores account status.

DENY: no token
Hardened implementation

State-aware check

Requires both an issued token and an active account.

DENY: missing or revoked authority

What the model demonstrates

After account deletion, the fragile implementation still says ALLOW because it only checks whether a token exists. The hardened version denies access because the current account state no longer authorizes the request.

fragile_authorize(token):
return token.was_issued

hardened_authorize(token, account):
return token.was_issued and account.is_active

This is deliberately simplified. Real applications must also evaluate expiration, revocation, signature verification, token audience, scopes, permissions, race conditions, and distributed state consistency.

Scope: This is an independently authored fictional demonstration. It is not an exploit against a real service, a reproduction of a confidential finding, or proof of any real vulnerability.
