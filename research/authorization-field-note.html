ENGINEERING / AUTHORIZATIONLAB REPORT — 001

When a token outlives its authority.

Three broken trust boundaries inside a small Python HTTP API: an object read by the wrong account, a member performing an admin action, and a deleted user whose old token still works.

IN THIS STORYThe setupObject ownershipRole boundariesSession lifecycleFix and retestWhat it proves

A request can carry a valid credential and still be unauthorized. That distinction is easy to write down and surprisingly easy to miss when a handler checks only whether a token exists.

I built an intentionally vulnerable local API to make that distinction visible through HTTP, not just diagrams. There are three fictional identities, a handful of endpoints, and two server modes: vulnerable and fixed.

SCOPE AND EVIDENCE

Every account, credential, object, request and response in this article belongs to a deliberately fictional localhost application. This is not an assessment of a real client or a reproduction of any confidential bug bounty endpoint.

01 / EXPERIMENT

Define the boundary before testing it.

The experiment asks three concrete questions: can Alice read Bob's order? Can an ordinary member create an administrative invitation? Can a deleted account continue to authorize requests with an earlier token?

02 / OBJECT OWNERSHIP

Authenticated as Alice. Reading Bob's order.

In the vulnerable handler, a recognized token is enough. It does not enforce that the requester owns the order. In fixed mode, the resource is accessible only to its owner or an authorized administrator.

The key observation is not the status code alone. It's that the authorization decision changes when object ownership is checked.

03 / FUNCTION AUTHORIZATION

A valid member shouldn't create admin invitations.

The second test invokes an endpoint intended for an administrator using Alice's member credential. A vulnerable implementation checks that the request is authenticated but does not require the right role.

This is broken function-level authorization, not a mass-assignment example. The control is the permission to call the operation itself.

04 / ACCOUNT STATE

The account is gone. The token isn't.

The third case exercises a token after the account is marked deleted. The broken implementation trusts the historical token record without evaluating current account state. The fixed version rejects it.

05 / REGRESSION

Reproduce, change the rule, replay.

The project includes automated tests that start temporary localhost servers and assert behavior in both modes. Replaying the same operation against the fixed mode makes the intended policy explicit.

06 / LIMITATIONS

What the experiment does not prove.

The demo tokens are intentionally unprotected strings. The example does not demonstrate a remotely exploitable account takeover, an attack on a real organization, or any production severity rating. In a real system, token acquisition, expiry, revocation, role evaluation and concurrency would require additional evidence.

THE LESSON

An HTTP 200 is an observation, not a security conclusion. The useful question is which authority the application actually checked, and which authority the operation required.
