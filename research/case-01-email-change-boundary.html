01 / 08Account lifecycleOut of scope

An email change that trusted the session too much

SAP/OData-style account lifecycle · sensitive profile update

I tested an authenticated profile-update operation that appeared to let the current session change the primary email address without a separate re-authentication or confirmation step. The exported report includes a detailed description of an observed HTTP 204 response and an attached-video reference.

RESEARCH TYPEReal investigation · sanitized
REVIEW OUTCOMEOut of scope
EVIDENCE LEVELEvidence: documented behavior, unproven exploit chain
01 / Research question

The hypothesis

A logged-in session could change a recovery-critical account attribute without fresh proof of user intent. The identifier used in the resource path appeared disconnected from the account being modified, adding an identity-mapping question.

Sequence under investigation

  1. Authenticated account session
  2. Send profile update with replacement email
  3. Server reports HTTP 204
  4. Original-account re-verification step not observed
02 / Technical reconstruction

The request and the boundary

Reconstructed sample. Hostnames, paths, identifiers and payload values below are synthetic. This is a technical representation of the tested concept, not an original production HTTP capture.

Illustrative request

PATCH /api/profile/records/{record-id} HTTP/1.1
Host: api.example.test
Authorization: Bearer <test-session>
Content-Type: application/json

{"primaryEmail":"new-owner@example.test"}

Observed / available response evidence

HTTP/1.1 204 No Content

03 / Security reasoning

Which invariant matters?

Changing a recovery-critical identity attribute should require an appropriately authorized principal and a policy-driven verification step. The request record ID must not accidentally obscure the account actually modified.

What the source record supports

The submission describes immediate email modification and HTTP 204. The researcher later reported that similar requests returned HTTP 403 with CSRF enforcement; this is a reported comparison, not independent proof of a deployed fix.

04 / Reviewer feedback

Where the proof ended

Triage treated the scenario as requiring an already-compromised account or physical/session access, which program rules excluded. The archive does not demonstrate an independent remote attacker acquiring that session and completing the claimed ATO.

RECORDED RESULT

Closed out of scope. No accepted remote ATO and no confirmed remediation attribution.

05 / Engineering takeaway

What changed in my methodology

A state-changing HTTP success can be real while the complete attack chain remains unproven. Capture the session precondition, attribute-change proof, and separate impact evidence.
