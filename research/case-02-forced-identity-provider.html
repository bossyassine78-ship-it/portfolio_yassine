Controlling identity-provider routing through OIDC parameters

OIDC authorization request · login-flow routing

I tested whether changing an OIDC request parameter could influence which upstream identity provider handled a login. The researcher notes describe a crafted authorization URL that steered the sign-in flow toward a different provider.

RESEARCH TYPEReal investigation · sanitized
REVIEW OUTCOMEOut of scope
EVIDENCE LEVELEvidence: recorded researcher claim and triage feedback
01 / Research question

The hypothesis

A client-specific authorization flow should constrain which external identity providers it accepts; a caller-controlled request hint should not silently override that constraint.

Sequence under investigation

  1. Start authorization flow
  2. Alter identity-provider selection hint
  3. Observe upstream IdP routing
  4. Test whether the client accepts unintended identity result
02 / Technical reconstruction

The request and the boundary

Reconstructed sample. Hostnames, paths, identifiers and payload values below are synthetic. This is a technical representation of the tested concept, not an original production HTTP capture.

Illustrative request

GET /oauth2/authorize?client_id=client-demo&response_type=code&acr_values=idp:alternate&state=<client-generated> HTTP/1.1
Host: login.example.test

Observed / available response evidence

HTTP/1.1 302 Found
Location: https://alternate-idp.example.test/authorize?...

03 / Security reasoning

Which invariant matters?

The authorization server must enforce client-specific permitted IdPs and bind the returned identity to a valid transaction. A caller-supplied routing hint cannot substitute for that policy.

What the source record supports

The follow-up commentary asserts that modifying acr_values caused routing to an alternate IdP and that a demonstration video was available.

04 / Reviewer feedback

Where the proof ended

Triage requested a working proof of user or company impact and rejected a hypothetical scenario that depended on a separate IdP configuration problem. A bypass of state validation was asserted but not independently demonstrated in this export.

RECORDED RESULT

Closed out of scope. IdP switching by itself was not accepted as proven compromise.

05 / Engineering takeaway

What changed in my methodology

Separate controllable protocol parameters from actual authentication-boundary violations. Demonstrate identity confusion or a security-relevant consequence, not just a changed redirect.
