Testing rate limits against GraphQL alias batching

GraphQL field aliases · per-request vs per-operation controls

This submission explored whether GraphQL aliases could turn a single HTTP request into many backend resolver calls and bypass request-count-based controls. The title also identified a potential tenant-enumeration effect.

RESEARCH TYPEReal investigation · sanitized
REVIEW OUTCOMEOut of scope
EVIDENCE LEVELEvidence: title and triage history; original payload not available
01 / Research question

The hypothesis

A limiter that counts only HTTP requests may miss multiple sensitive operations executed inside one GraphQL document.

Sequence under investigation

  1. Prepare one GraphQL operation
  2. Repeat sensitive field using aliases
  3. Compare behavior with sequential requests
  4. Check whether responses disclose sensitive tenancy data

03 / Security reasoning

Which invariant matters?

Apply resource-appropriate rate limiting, authorization and privacy controls per sensitive resolver invocation, not only per outer HTTP envelope.

What the source record supports

The export preserves the original report title, submitted category and triage exchanges, but not the technical PoC body or actual response traces.

04 / Reviewer feedback

Where the proof ended

Triage closed the submission under an exclusion for verbose responses without sensitive information. The export does not verify a meaningful tenant enumeration or an exploitable bypass.

RECORDED RESULT

Closed out of scope. No validated sensitive-data disclosure in the available record.

05 / Engineering takeaway

What changed in my methodology

For batched APIs, compare the counting unit: HTTP request, GraphQL operation, resolver call and business action. Build an evidence table with response counts and disclosed information.
