When an invalid callback transaction still controlled navigation

Identity-provider callback · fallback redirect validation

In a responsible-disclosure investigation, I reported an open redirect involving an identity callback error path. A fabricated or invalid transaction identifier combined with a caller-controlled redirect URL created a navigation boundary problem. Independent triage later reproduced the issue and forwarded it to the company.

RESEARCH TYPEReal investigation · sanitized
REVIEW OUTCOMEResolved
EVIDENCE LEVELEvidence: independent reproduction + accepted retest
01 / Research question

The hypothesis

When an authentication transaction is invalid, callback error handling must not allow user-provided navigation targets to replace trusted redirect destinations.

Sequence under investigation

  1. Send callback with invalid transaction reference
  2. Include external redirect URL parameter
  3. Observe whether an external Location is emitted
  4. After remediation, replay with multiple fabricated identifiers
02 / Technical reconstruction

The request and the boundary

Reconstructed sample. Hostnames, paths, identifiers and payload values below are synthetic. This is a technical representation of the tested concept, not an original production HTTP capture.

Illustrative request

GET /identity/callback?transactionId=invalid-value&redirectUrl=https%3A%2F%2Fredirect.example.test HTTP/1.1
Host: idp.example.test

Observed / available response evidence

INITIAL BEHAVIOR: open redirect reproduced by triage
RETEST: callback returns an error response
RETEST: no attacker-controlled Location header
RETEST: repeated with another fabricated UUID

# Exact production URLs and raw wire captures are withheld.
03 / Security reasoning

Which invariant matters?

Callback error paths must enforce redirect-target validation independently of whether the referenced transaction exists. Invalid transaction state must not activate unsafe fallback navigation.

What the source record supports

The preserved export shows independent reproduction, forwarding to the company, a later retest request, accepted retest, and the researchers observation that the original redirect was no longer reproducible.

04 / Reviewer feedback

Where the proof ended

Original raw HTTP traffic is not visible in the export, so this case does not invent precise original status codes or headers. An open redirect is not equivalent to proven OAuth token theft.

RECORDED RESULT

Accepted and resolved. The retest was accepted and awarded €50 as a retest bounty; the original disclosure carried €0 bounty.

05 / Engineering takeaway

What changed in my methodology

Retesting matters. I checked not just one input but another fabricated transaction identifier and verified the absence of an attacker-controlled Location header.
