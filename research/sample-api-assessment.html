YASSINE / LAB ASSESSMENT / 001

Authorization assessment: complete technical lab report.

A client-facing report format, applied to a deliberately vulnerable fictional API. This page shows what was tested, the precise evidence, what it does and does not prove, and how a fix is verified.

Python 3HTTP APILocalhost only3 test cases
Executive summary

Three authorization boundaries failed in vulnerable mode.

This exercise covers object access control, role-restricted operations and credential validity after account deletion. The supplied regression suite checks these deliberately introduced defects against corrected behavior using actual local HTTP calls.

Important: Risk labels describe this fictional test model only. They are not production CVSS scores, and this exercise is not evidence of a vulnerability at any real organization.

Scope & method

Tested surface

127.0.0.1:8765 with synthetic accounts Alice, Bob and Admin; fake token strings; orders 4001 and 4002; admin invitation endpoint.

Testing method

Establish a control identity, replay endpoint calls with a second identity, inspect response status and payload, change account state, then repeat in --mode fixed.

No production hosts, confidential report exports, actual credentials, or third-party user information were used to build this sample.

AS-01 / BOLA / IDORHIGH (LAB)

Object-level authorization

An authenticated member reads an order belonging to another member.

Proof: request

GET /api/orders/4002 HTTP/1.1
Host: 127.0.0.1:8765
Authorization: Bearer alice-demo-token

Observed response (vulnerable mode)

HTTP/1.0 200 OK
Content-Type: application/json

{"order":{"owner":"bob","item":"Keyboard","total":60}}

Expected response (fixed mode)

HTTP/1.0 404 Not Found

{"error":"NOT_FOUND"}

Security impact and evidence limit

An authenticated Alice can inspect Bob’s order without being its owner. In a real application, impact depends on actual data sensitivity and identifier accessibility.

Remediation

Apply a server-side authorization decision to the fetched object: order.owner == principal, or a narrowly defined administrative permission. Do not rely on UI visibility.

Verification

Run the same request under both modes. Alice should receive 404 in fixed mode, Bob should receive 200.

AS-02 / BFLAHIGH (LAB)

Function-level authorization

A non-admin member can create an admin invitation.

Proof: request

POST /api/admin/invitations HTTP/1.1
Host: 127.0.0.1:8765
Authorization: Bearer alice-demo-token
Content-Type: application/json

{"email":"demo@lab.invalid"}

Observed response (vulnerable mode)

HTTP/1.0 201 Created

{"invitation":{"id":1,"email":"demo@lab.invalid","role":"admin","created_by":"alice"}}

Expected response (fixed mode)

HTTP/1.0 403 Forbidden

{"error":"FORBIDDEN"}

Security impact and evidence limit

An authenticated non-admin can create an invitation carrying the administrator role in the fictional application. The lab does not implement invitation redemption, so actual privilege escalation through invitation acceptance is not demonstrated.

Remediation

Require role/permission checks in the server-side invitation handler, not just token presence. Restrict invited roles and validate the requested authority.

Verification

Normal member gets 403 in fixed mode; admin-demo-token still gets 201.

AS-03 / ACCOUNT STATEMEDIUM (LAB)

Session lifecycle invalidation

A deleted account’s credential still authorizes account reads.

Proof: request

DELETE /api/me HTTP/1.1
Authorization: Bearer alice-demo-token

GET /api/me HTTP/1.1
Authorization: Bearer alice-demo-token

Observed response (vulnerable mode)

HTTP/1.0 200 OK

{"name":"alice","role":"member","deleted":true}

Expected response (fixed mode)

HTTP/1.0 401 Unauthorized

{"error":"UNAUTHENTICATED"}

Security impact and evidence limit

The same bearer credential remains accepted after an authenticated account deletion. This is an account-lifecycle authorization failure, not proof of third-party token acquisition or account takeover.

Remediation

Bind authenticated identities to current account state; invalidate or revoke session credentials during deletion and repeat the check on every protected operation.

Verification

Delete Alice in a fresh server instance, then request /api/me with the same credential: expect 401 in fixed mode.

Verification & delivery

Reproduce it yourself.

Run the included labs/authz-lab/ project locally. The same tests exercise both the vulnerable and fixed modes, with no external dependencies.

cd labs/authz-lab
python3 -m unittest -v test_lab.py

# Manual comparison
python3 server.py --mode vulnerable
# stop with Ctrl+C, then
python3 server.py --mode fixed

The deliverable format used here is: scope → invariant → request → response → observed behavior → realistic impact → remediation → retest. For a real assessment, severity and final conclusions would depend on verified access paths, business context and the customer’s authorization.
