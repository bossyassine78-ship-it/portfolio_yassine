ORIGINAL REPRODUCIBLE LAB / 001

Authentication isn't authorization.

A deliberately broken, localhost-only Python API demonstrates three separate trust boundaries with actual HTTP requests, expected results and fixed-mode checks.

Python 3HTTPObject and function authorization
All tokens, users, requests and responses below are fictional and are generated locally. This is not a reproduction of a private program's endpoints or a claim about a real target.

01 / Object ownership (BOLA)

Alice possesses a valid demo token. She requests Bob's order. The vulnerable implementation checks only that the token maps to an account, not that the account owns the object.

GET /api/orders/4002 HTTP/1.1 Host: 127.0.0.1:8765 Authorization: Bearer alice-demo-token VULNERABLE: HTTP 200 {"order":{"owner":"bob","item":"Keyboard","total":60}} FIXED: HTTP 404 {"error":"NOT_FOUND"}

Correct invariant: the caller must be the resource owner or an explicitly authorized administrator. Possession of any valid token is insufficient.

02 / Function-level access (BFLA)

An ordinary member attempts an administrative invitation operation.

POST /api/admin/invitations HTTP/1.1 Host: 127.0.0.1:8765 Authorization: Bearer alice-demo-token Content-Type: application/json {"email":"candidate@lab.invalid"} VULNERABLE: HTTP 201, invitation.role = "admin" FIXED: HTTP 403, {"error":"FORBIDDEN"}

Correct invariant: authorization to call a privileged function must be evaluated for that function, independent of login state. This is not a mass-assignment example.

03 / Stale identity state

After the account is marked deleted, an old demo token is reused. The vulnerable implementation continues treating the historical token as authority. Fixed mode checks the current account state.

DELETE /api/me Authorization: Bearer alice-demo-token HTTP 200 {"deleted":"alice"} GET /api/me Authorization: Bearer alice-demo-token VULNERABLE: HTTP 200, deleted = true FIXED: HTTP 401, {"error":"UNAUTHENTICATED"}

Impact limitation: a stale token replay is an account-lifecycle authorization problem, but does not establish a remotely exploitable takeover without an attacker-accessible token acquisition path.

Run, replay, refute

Run the API in both modes and verify the same requests yield different authorization outcomes. The project includes repeatable test assertions against real localhost HTTP responses.

cd labs/authz-lab python3 server.py --mode vulnerable # In a separate terminal, from the same directory: python3 -m unittest -v test_lab.py # Stop the server and compare: python3 server.py --mode fixed

The tests automatically launch their own temporary server, so they can also run without the manually launched instance.
